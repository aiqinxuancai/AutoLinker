# 编译错误定位验证（2026-09-12）

测试工程：`D:\git\AutoLinker\eproj\e-console-exe-new-proj.e`。
环境：易语言 e5.95，AutoLinker `fne_release / Win32`，通过
`http://127.0.0.1:19207/mcp` 初始化会话、选择实例、刷新镜像、读取/编辑/编译。
未直接修改 `.e` 二进制制造错误；测试前备份原文件，测试后恢复。

## 复现

使用 MCP 将启动子程序的 `输出行 (“Hello！”)` 改为
`输出行 (诊断测试_未定义变量)`，连续编译两次。

两次均收到正确的 `错误(30)`，但原来的 `caret_row=4` 对应的
`caret_line_text` 第一次为空，第二次错误地指向 `.子程序 _启动子程序...`。
该字段直接用 IDE 原生行号索引整页文本，混淆了两套坐标。
此外，MCP 文本摘要不会包含错误位置，而只有完整结构化响应保留旧光标字段。

## 修复契约

- 用原生范围格式化器读取错误行，避免剪贴板和整页选择。
- 前缀映射需要与规范化整页逐行核实；无法使用前缀时采用唯一完整行匹配。
- 文件映射还验证程序树目标的编辑器对象与当前错误页对象相同。
- 单个源错误明确引用的符号必须出现在原生行中，才公开经过验证的位置。
- 不具备这些证据时返回空位置及 `location_verified=false`，不将旧光标冒充错误位置。
- 编译前清空并验证输出控件基线，防止相同错误和历史输出的归属不明。
- `diagnostics` 同时提供给结构化 MCP 客户端和只消费文本摘要的客户端。

## 09:16:50 卡死调用链复核及 SDK 优先读取

历史文件 `C:/Users/aiqin/OneDrive/e5.6/AutoLinker/Log/autolinker_pid23224.log`
记录：09:16:20.345 请求编译，09:16:50.391 工作线程输出 30 秒等待日志，
09:16:50.403 编译等待以 `request_inactive` 结束。
`ai_code_fetch_last_pid23224.log` 则明确记录：

```text
[AI-CODE-FETCH] session-start scene=GetCurrentPageCode trace=0 time=2026-9-12 9:16:50.420
[STEP] enter GetCurrentPageCode
[STEP] caret row=0 col=0
[STEP] ReadClipboardText ok=1 len=14053 ...
```

因此旧编译后诊断确实无条件调用了 `GetRowFullText -> GetCurrentPageCode`，
进入了整页选择、复制、读剪贴板和 RAII 恢复剪贴板的路径，没有优先使用真实页
内部格式化器。日志已证明读剪贴板成功，但没有当时的线程栈，不能进一步证明
唯一阻塞点是剪贴板恢复还是后续结果交付。

另一个 agent 对工作线程等待日志的修改应保留：旧代码持有 `request->mutex`
调用 `WriteAndIde -> OutputStringToELog -> AppendOutputWindowLine -> SendMessage`；
主线程交付结果又需要同一把锁，存在实际跨线程锁互等。改为释放请求锁并只写
文件日志，是移除该锁环，而非仅增加超时保护。

当前调用链是：

1. `IDEFacade::GetProgramText(-1, -1)` 调用 SDK 的 `FN_GET_PRG_TEXT`，先查询缓冲区大小，
   再读取当前光标位置文本，不改变选区或剪贴板。
2. 原生范围格式化仅用于验证 SDK 文本与原生行一致；SDK 不可用时才作为内容回退。
3. 整页使用与真实页读取相同的直接格式化器，核实行号、文件对应编辑器对象，
   返回错误行前后各两行上下文，`>` 标出错误行，保留源码原始缩进。
4. 没有剪贴板回退；命令未启用时编译入口立即返回 `compile_command_not_enabled`，
   不把无效调度当成已启动编译后再空等保存对话框。该预检查不用于推断历史会话状态。

SDK 优先后的启动子程序、第二个子程序、嵌套及重复代码行四种 MCP 回归均通过。
`code_source=ide_sdk_fn_get_prg_text`；每个节选行均与 MCP `read_real_file` 返回值
逐字核对，而不只比较错误行。无公开子程序的 DLL 编译错误保留消息并返回
`location_verified=false`，不会将程序集标题伪装为出错代码。

专项测试在整个错误编译期间由外部进程持有系统剪贴板，仍在 1 秒内完成定位；
编译前后剪贴板序号相同。原始结果见 `.tmp/compile-diagnostics/sdk-clipboard-lock-test.json`。
最后恢复正确代码并静态编译成功。SDK 版本的 `fne_release / Win32` 构建及诊断 C++
自检通过。


## 多程序集复杂代码验证与旧标题修复

在同一个 `.e` 测试工程内通过 MCP 写入三个程序集，最初真实页读回共 **3,798 行**：
主程序集 1,330 行，两个辅助程序集各 1,234 行，共 90 个计算子程序及启动子程序。
每个计算子程序包含参数、局部变量、数组、中文注释、三层循环/条件嵌套和判断分支。
启动子程序引用全部 90 个计算子程序，正确基线静态编译通过。

每页有 90 处完全相同的 `累计 ＝ 累计 ＋ 复用变量`。通过仅移除目标子程序中
该变量的声明及初始化来制造错误，确保错误只属于目标子程序，前面同名文本仍合法。
预期位置由编辑后的 MCP `read_real_file` 和明确指定的子程序边界独立计算。

这项测试发现并修复了一个单页测试未暴露的问题：编译自动跳转到辅助程序集时，
MDI 标题可能仍显示创建时的旧默认名称“程序集3”。此前代码和原生行到源码行的
映射已经正确（第 1,088 行），但依据旧标题寻找镜像文件失败，诊断返回空文件位置。
现在从直接格式化所得真实源码 `.程序集` 声明解析名称，再核对映射目标与出错页的
编辑器对象身份；`diagnostics.page_name` 不再依赖过期窗口标题。
