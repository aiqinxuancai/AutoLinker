# Issue #26：常量整页写入验证

验证日期：2026-09-16。环境为 e5.95 加密狗版、VS2026、
AutoLinker `fne_release / Win32`；修复前代码为 `3df7c96`（5.1.13）。
Issue：https://github.com/aiqinxuancai/AutoLinker/issues/26 。

## 先复现再修复

使用 `eproj/e-console-exe-new-proj.e` 的独立副本，经本地 MCP 19207
写入 issue 中四条声明。请求和响应使用 UTF-8。

实测触发条件比 issue 描述更具体：

- 保留 `.版本 2` 时，原样整页重写保持四槽，没有复现新增空槽。
- 只提交四条 `.常量` 声明、缺少版本头时，四条声明全部变成五槽。
- 再写入带版本头的声明，恢复四槽；重复缺版本头的写入再次变成五槽。
- 以上错误写入返回 `ok=true / verified=true`。
- 另测得有版本头但没有末尾换行时，写入返回哈希与真实读回哈希不同。

因此已确认“新增空槽”和“静默成功”现象存在，但未复现 issue 所称的
“输入确实包含 `.版本 2` 仍产生第五槽”。不能据此断言报告者实际提交的请求内容。

IDE 的原生文本解析在没有版本声明时使用旧布局。整页写入直接传入请求文本，
局部编辑通常保留读取所得版本头，导致两种调用看起来行为不同。
常量固定表还跳过了最终读回校验，随后调用层用请求文本作为成功结果和哈希，
掩盖了 IDE 实际写入内容的差异。

## 修改

在 `ReplaceRealPageCodeByProgramTreeItemData` 的常量页入口补齐缺失版本头，
已有版本声明保持原样。处理发生在长文本保护计划和原生解析之前。
不对常量行做逗号替换，也不把旧五槽格式强制改成四槽。

移除常量表最终写入跳过校验的特例。成功结果来自真实读回文本，哈希也以它为准；
发现结构不一致时执行既有回滚流程。长文本保护中的中间暂存阶段仍保留原有行为。

空表首建的完整回归还发现：镜像文件仍为空时，后续局部编辑会重复创建默认的
“常量1”。在镜像提示空表时增加真实页声明检查，已有声明就不再触发首条目创建。

## 重复运行

先复制一个测试 `.e` 文件，用装有待验证支持库的 e5.95 打开副本，再执行：

```powershell
python scripts/test_const_page_write.py --project D:\path\test-copy.e --output .tmp\const-page-regression
```

脚本明确选择该工程对应的 MCP 实例，会覆盖这个副本的常量表，结束后保留四条
测试常量供保存、重开和独立导出验证；不要指向需要保留内容的工程。
脚本直接断言实际声明、写入/读回哈希、两种局部编辑和失败回滚，失败即退出。

额外观察：测试任意过期 `expected_base_hash` 时，外部写入预览流程会刷新基准后继续
写入（`AIChatFeature.cpp` 的现有行为）。它独立于本次槽位和写后校验问题，未纳入
本次修改，也不计作已通过的 CAS 拒绝测试。
